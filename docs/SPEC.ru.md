# TextSieve — спецификация реализации

[English](SPEC.md) | Русский

## Продукт

**TextSieve** — детерминированный фильтр качества и безопасности текста для JavaScript/TypeScript.

Краткое описание:

> Обнаруживает ненормативную лексику, явные оскорбления, бессмысленный текст, спам, некорректный ввод и очевидные злоупотребления без ИИ, API и сетевых запросов.

Целевые среды выполнения: браузер, Node.js 20+, Bun, Edge/Workers; Deno — по возможности.

## Публичный API

```ts
import { createSieve, en, ru } from "textsieve";

const sieve = createSieve({
  languagePacks: [ru, en],
  expectedLanguage: "ru",
  safetyLanguages: ["ru", "en"],
  transliteration: {
    enabled: true,
    targets: ["ru"]
  },
  preset: "public-form"
});

const result = sieve.inspect("ах ты bitch");
```

```ts
type Decision = "allow" | "review" | "reject";

interface InspectionResult {
  decision: Decision;
  score: number; // 0..100; 100 = чистый текст высокого качества
  input: string;
  normalized: string;
  sanitized: string;
  signals: Record<string, number>; // каждый сигнал 0..1
  issues: Issue[];
  meta: InspectionMeta;
}
```

Вспомогательные методы:

```ts
sieve.inspect(text);
sieve.check(text);
sieve.normalize(text);
sieve.sanitize(text);
```

## Языковая модель

Не используйте один `locale` для управления всем поведением.

```ts
interface LanguageOptions {
  languagePacks?: readonly LanguagePack[];
  expectedLanguage?: string;
  safetyLanguages?: readonly string[];
  transliteration?: {
    enabled: boolean;
    targets?: readonly string[];
  };
}
```

### `expectedLanguage`

Проверяет, соответствует ли текст языку, ожидаемому для поля.

Для `ru`:

- `Привет, всё отлично` → норма
- `React разработчик` → норма
- `Hello how are you today` → сигнал несоответствия языка

### `safetyLanguages`

Определяет, какие пакеты ненормативной лексики и оскорблений запускаются независимо от ожидаемого языка.

`ах ты bitch` должно обнаруживаться английскими правилами безопасности даже в русскоязычной форме.

### Транслитерация и варианты

Никогда не транслитерируйте весь исходный текст с его заменой.

У токенов могут быть варианты:

```ts
interface TokenVariant {
  value: string;
  source: "normalized" | "deobfuscated" | "translit-ru" | "leet" | "joined";
}
```

Примеры:

- `suka` → `сука`
- `cyka` → `сука`
- `blyat` → `блять`
- `nahui` → `нахуй`

## Конвейер обработки

```text
исходный текст
  -> проверка Unicode
  -> нормализация
  -> очистка
  -> токенизация
  -> варианты токенов и кандидаты
  -> статистика текста
  -> общие правила
  -> языковые правила безопасности
  -> сигналы бессмысленного текста
  -> агрегация оценки
  -> политика
  -> allow/review/reject
```

Этапы должны оставаться модульными.

## Интерфейс правила

```ts
interface TextRule {
  readonly id: string;
  inspect(context: RuleContext): RuleResult | null;
}

interface RuleContext {
  input: string;
  normalized: string;
  sanitized: string;

interface RuleResult {
  rule: string;

```

Правила не должны изменять общий контекст.

## Поиск ненормативной лексики и оскорблений

Храните ненормативную лексику и явные оскорбления как отдельные сигналы.

Консервативно поддерживайте:

- границы токенов;
- Unicode-нормализацию;
- вставленные разделители и пробелы;
- повторяющиеся символы;
- распространённый литспик;
- варианты транслитерации;
- смешение алфавитов и омоглифы там, где это безопасно;
- исключения из списка разрешённых слов.

Примеры: `блять`, `бл*ть`, `б л я т ь`, `бл@ть`, `бляяяять`, `bitch`, `b!tch`, `suka`, `cyka`, `blyat`.

### Быстрый поиск по словарю

Для большого числа известных слов и шаблонов реализуйте или оцените скомпилированный многопаттерновый поиск **Ахо — Корасик** либо столь же эффективный детерминированный алгоритм. Не выполняйте N независимых проходов `includes()` по всему тексту.

Компилируйте статические словари при создании sieve или языкового пакета, а не при каждой проверке.

Сохраняйте метаданные шаблона, чтобы совпадение содержало:

- правило;
- язык;
- каноническую форму;
- серьёзность;
- исключения.

### Нормализация обходов фильтра

Создавайте отдельные кандидаты для известных способов обхода:

- пробелы между буквами;
- визуально похожие символы и цифры;
- повторяющиеся символы;
- транслитерация;
- консервативное восстановление границ склеенных слов.

Не исправляйте опечатки без ограничений. Широкий нечёткий поиск создаёт слишком много ложных срабатываний.

## Бессмысленный текст

Это одно из ключевых отличий продукта.

Не определяйте бессмысленный текст как «слово отсутствует в словаре».

Комбинируйте:

- повторения символов;
- повторения токенов;
- вероятность клавиатурной последовательности;
- баланс гласных и согласных;
- распределение письменностей;
- длину токенов;
- лексическое разнообразие;
- энтропию;
- плотность пунктуации;
- компактную оценку правдоподобия символьных n-грамм;
- долю известных слов только как слабый сигнал.

Примеры:

- `купил товар, всё отлично` → низкий сигнал
- `ывпавфыапфыва` → высокий сигнал
- `asdfghjkl` → очень высокий сигнал
- `React TypeScript SDK` → низкий сигнал

Поставляйте компактную статистику RU/EN n-грамм в языковых пакетах; не выполняйте инференс во время работы.

## Безопасность Unicode

Обнаруживайте:

- символы нулевой ширины;
- управляющие символы двунаправленного текста;
- подозрительные управляющие символы;
- невидимые повторения;
- смешение письменностей внутри токена;
- простую подмену омоглифами.

`React разработчик` — допустимый многоязычный текст.

`pаypal` со смешением латиницы и кириллицы внутри одного токена подозрителен.

## Правила спама и качества

MVP включает:

- повторяющиеся символы;
- повторяющиеся слова и фразы;
- клавиатурные последовательности;
- чрезмерное использование верхнего регистра;

- чрезмерное число email и телефонов;
- низкое лексическое разнообразие.

## Производительность

Проверка обычного короткого текста формы должна оставаться синхронной.

Бенчмарки:

- 20, 100, 500, 2 000 и 10 000 символов.

Отслеживайте:

- среднее время;
- p95;
- операций в секунду;
- размер bundle;
- размер языковых пакетов.

Проверяйте пути регулярных выражений с пользовательскими данными на ReDoS.

## Тестирование

Для каждого правила необходимы:

- положительный пример;
- отрицательный пример;
- пример ложного срабатывания;
- пограничный пример;
- обфускация, если применима;
- Unicode, если применим.

Корпус ложных срабатываний должен включать как минимум `TypeScript`, `Next.js`, `PostgreSQL`, `OAuth2`, `OpenAPI`, `npm`, `pnpm`, `dev-ik`, `React/Node.js разработчик`, а также реалистичные имена, компании, адреса и продукты.

Предпочитайте семантические проверки тестам, основанным только на снимках.

Проверки на frontend служат только для UX. Документация должна явно требовать повторять принудительную проверку на сервере.

## Конфиденциальность

Сетевые запросы и телеметрия отсутствуют. TextSieve не передаёт пользовательский текст за пределы процесса приложения.
